## دروازه پذیرش پیش از استفاده واقعی

1. تست، lint و assemble در اجرای لینک‌شده سبز شده‌اند؛ APK همان اجرا برای آزمون نصب شود.
2. موارد زیر روی Android API 24 و 34 و یک نسخه جدیدتر، با سیم‌کارت آزمایشی و گیرنده دارای رضایت انجام شوند.
3. قرارداد endpointها و کنترل مالکیت با افزونه واقعی بررسی شود؛ افزونه در این مخزن موجود نیست.

| سناریو | انتظار |
| --- | --- |
| ورود معتبر، رمز غلط، پاسخ خراب، HTTP و redirect | ورود معتبر کار کند؛ خطا آشکار شود؛ اطلاعات ورود به مقصد redirect منتقل نشود |
| درخواست کند → خروج → ورود حساب دوم | داده، نتیجه درخواست و ارسال حساب اول وارد حساب دوم نشود |
| 401 در GET، fetch و update | نشست پاک، رابط ورود و توقف ارسال؛ نه حلقه خطای بی‌نهایت |
| رد SEND_SMS / لغو مجوز هنگام کار | بدون مجوز، صف جدید برداشت/ارسال نشود؛ اجازه از اقدام صریح کاربر درخواست شود |
| رد POST_NOTIFICATIONS در API 33+ | شروع foreground طبق سیاست اندروید؛ نبود مجوز اعلان باعث crash نشود |
| توقف در زمان درخواست مجوز یا تعویض حساب پیش از پاسخ مجوز | callback یا intent قدیمی هیچ ارسال جدیدی را شروع نکند |
| توقف و شروع سریع همان حساب | cleanup اجرای قبلی درخواست جدید را باطل نکند؛ یک مصرف‌کننده صف فعال بماند |
| خطای 403/404/422 در سرویس | توقف با پیام قابل مشاهده، بدون retry بی‌نهایت |
| خطای 408/429/5xx | backoff محدود به ۲ دقیقه؛ تکرار همگام‌سازی بدون ارسال دوباره SMS |
| لمس چندباره شروع/ساخت صف | یک مصرف‌کننده صف؛ یک درخواست ساخت فعال؛ تأیید دوباره هنگام درخواست ممکن نباشد |
| متن کوتاه، فارسی بلند، emoji، چند بخش | شمارش با API سیستم؛ `sent` فقط پس از موفقیت همه بخش‌ها |
| شکست یک بخش، نبود آنتن/سیم‌کارت پیش‌فرض | موفقیت کاذب یا ارسال مجدد خودکار رخ ندهد |
| نرسیدن callback پس از ۹۰ ثانیه | وضعیت نامشخص (`sending`)؛ بدون ارسال دوباره همان شناسه |
| قطع شبکه بعد از ارسال و قبل از update | فقط update تکرار شود؛ پس از بازشدن دوباره نیز پیامک تکرار نشود |
| کشته‌شدن فرایند پس از ثبت sending | شروع مجدد دستی؛ آیتم مبهم بازفرستاده نشود |
| توقف از اعلان/رابط و خروج | ارسال پیام بعدی متوقف؛ callback دیررس باعث شروع مجدد نشود |
| قطع ساخت صف بین دو گروه | بررسی صف قبل از retry؛ صف نیمه‌ساخته ممکن است وجود داشته باشد |
| تغییر جهت، چرخش، Back، فیلتر، بیش از ۱۰۰ مخاطب | رابط بدون crash، نمایش کامل لیست؛ درخواست‌های رهاشده رابط ادامه مستقل ندهند |
| نوروز، کبیسه، مرز ماه ۳۱روزه، DST و offset | برچسب امروز/دیروز و زمان محلی صحیح |
| حساب دیگر درخواست ID گروه/صف کاربر اول | **سرور** باید دسترسی را رد کند؛ حفاظت فقط در کلاینت کافی نیست |

## ریسک‌های باقی‌مانده

- تضمین exactly-once بین مودم، سیستم‌عامل و سرور بدون قرارداد idempotency/ack مشترک ممکن نیست. این نسخه در ابهام، عدم ارسال مجدد را انتخاب می‌کند، حتی اگر پیام واقعاً ارسال نشده باشد.
- دفتر محلی تا زمانی که داده‌های برنامه حفظ شوند معتبر است؛ دستگاه دوم یا نصب مجدد همان دفتر را ندارد. رکوردهای تأییدشده عمداً حذف خودکار ندارند تا شناسه برگشتی دوباره ارسال نشود؛ برای حجم بسیار زیاد، ذخیره‌سازی دیتابیسی و سیاست نگهداری مشترک با سرور لازم است.
- لغو coroutine نمی‌تواند درخواست HTTP یا پیام تحویل‌داده‌شده به مودم را برگرداند. timeout شبکه محدود است و نتایج نشست قبلی پذیرفته نمی‌شوند؛ تغییر سمت سرور که پیش‌تر ارسال شده ممکن است همچنان انجام شود.
- WorkManager، resume پس از reboot، delivery receipt، انتخاب سیم‌کارت، واردکردن مخاطب و انتشار فروشگاهی خارج از پیاده‌سازی فعلی‌اند.
